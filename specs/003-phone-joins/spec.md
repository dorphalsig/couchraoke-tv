## Clarifications

### Session 2026-08-18

- Q: `plan.md` says "a second phone joining an occupied session gets the specified rejection", but `tv_app.md` §2.6.15.1 caps the roster at 10 devices. How should the rejection gate read? → A: The roster cap is 10. The gate asserts an 11th device is rejected with `session_full` (per F15 `case_slot_taken`). The top-level `F15/transcript.jsonl`, which rejects a 3rd phone with `session_full`, is stale and contradicts both `case_slot_taken` and the 10-device cap.
- Q: `plan.md` requires a "specified close code" for protocol version mismatch, but `tv_app.md` never specifies one. → A: All rejections close with WebSocket code `1008` (Violated Policy), and the close reason carries the same code string as the `error` payload (e.g. `protocol_mismatch`).
- Q: Slice 1 declares GamePhase `Open` and `Error` only, but §4.1 has no `Open→Error` transition, so `Error` is unreachable in this slice. How is a session-start failure surfaced? → A: As a blocking modal that prevents gameplay and returns to the song-selection surface on dismiss. GamePhase remains `Open`; no new FSM transition is introduced.
- Q: §2.6.13 defines the join overlay as a modal over the Song List, which does not exist until Slice 3. What hosts it in Slice 1? → A: A minimal Song List shell — empty-state grid plus a header Join button — that later slices fill in. The overlay opens over it per §2.6.13.
- Q: Does Slice 1 include `clientId` reclaim on reconnect, or is that entirely Slice 12? → A: Slice 1 includes reclaim: a returning `clientId` reuses its existing roster entry and receives a new `connectionId`. Singer re-assignment, `playbackState` resend, and `DisconnectPaused` remain in Slice 12.

### Session 2026-08-19

- Q: Does a disconnected phone keep its place in the session roster and its capacity slot? → A: Yes, and the roster and the live connected list are two distinct things. The **session roster** is keyed by device identity, retains disconnected entries, and holds the capacity slot so the device still has its place for the next song. The **connected list** — what the overlay count and the protocol's `connectedDevices` report — drops the phone the moment its connection ends. A retained entry is released by Kick, by the session ending, or at the end of a song, where every entry with no live connection is dropped and its slot freed. Slice 1 has neither songs nor Kick, so within this slice a retained entry is never released; both release paths are specified here but enforced by the slices that introduce them.
- Q: A socket can pass join-code validation and then never send an introduction, holding a connection indefinitely. What bounds it? → A: Close it after 5 seconds without a valid introduction, with the same close code as a refusal and reason `invalid_message`. A pending connection has no device identity, so it never occupies a roster slot or counts toward capacity.
- Q: A TV box may have both wired and wireless networks up. Which address goes into the announcement and the QR code? → A: Accept connections on every interface, but advertise and encode only the IPv4 address of the network the TV is currently using for local traffic — one address, not a list. If there is no such usable address, session start fails through the existing blocking-notice path.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A phone finds the TV and joins the session (Priority: P1)

A host opens the app on the TV. The app immediately starts a session, shows a join code and QR code, and announces itself on the local network. A guest opens the companion app on their phone, which either finds the TV automatically on the LAN or scans the QR code, and connects. The guest's phone appears in the TV's connected list within a couple of seconds, and the guest's phone knows which session it is in and which slot it holds.

**Why this priority**: Nothing else in the product is reachable without it. Every later slice — song lists, previews, singing, scoring — depends on at least one phone being connected and identified. This is the first slice that produces something a person can watch happen.

**Independent Test**: Launch the app, run the real out-of-process peer against it over loopback with discovery enabled, and confirm the peer's device name appears in the TV's connected list and the peer received a session identity. No song, library, or playback capability is required.

**Acceptance Scenarios**:

1. **Given** the app has just launched and no phone is connected, **When** the host opens the join surface, **Then** a QR code and a two-word join code are displayed, and the connected count reads zero.
2. **Given** the app is advertising on the local network, **When** a phone searches for the service, **Then** it finds an advertisement carrying the join code and the protocol version, pointing at the TV's control port.
3. **Given** a phone has discovered or scanned the TV, **When** it opens a control connection using the correct join code and sends a valid introduction, **Then** the TV admits it, assigns it a unique connection identity, replies with the current session state including that identity, and the phone appears in the TV's connected list.
4. **Given** one phone is already connected, **When** a second phone joins with a different device identity, **Then** both phones appear in the connected list and the second phone receives a distinct connection identity.
5. **Given** a phone is connected, **When** its connection drops, **Then** it disappears from the connected list as the close is handled, while keeping its place in the session roster.

---

### User Story 2 - Bad or unwelcome connections are refused clearly (Priority: P2)

A phone that presents the wrong join code, an unsupported protocol version, or an incomplete introduction is turned away with a machine-readable reason rather than being silently dropped or silently admitted. Once the session is at capacity, further devices are refused for that reason.

**Why this priority**: This is the half of the join boundary that the previous attempt could not prove. Admission without rejection is not a working handshake — a server that accepts everything passes the same happy-path test. It is P2 only because a demo shows the happy path first.

**Independent Test**: Drive each rejection case from the real peer process over loopback and assert the exact reason code, the delivery of the refusal before the connection closes, and the close code. Independently, replay the F20 fixture cases against the message validator with no transport involved.

**Acceptance Scenarios**:

1. **Given** the session is open, **When** a phone connects with a missing or incorrect join code, **Then** it receives a refusal with reason `invalid_token` and the connection is closed.
2. **Given** the session is open, **When** a phone introduces itself with a protocol version other than the supported one, **Then** it receives a refusal with reason `protocol_mismatch` and the connection is closed.
3. **Given** the session is open, **When** a phone's introduction omits a required field, **Then** it receives a refusal with reason `invalid_message` and the connection is closed.
4. **Given** the session roster already holds the maximum number of devices, **When** a device the session has not seen before tries to join, **Then** it receives a refusal with reason `session_full`.
5. **Given** a phone is mid-handshake, **When** it sends a message the handshake does not expect, **Then** the connection is closed as a failed handshake rather than the message being ignored.
6. **Given** a connection has presented a valid join code, **When** it sends no introduction for 5 seconds, **Then** the TV closes it with reason `invalid_message`, and it never appeared in the connected list or consumed a roster slot.

---

### User Story 3 - A phone that drops off reclaims its place (Priority: P3)

A phone loses network briefly, or its app is backgrounded and returns. It reconnects on its own, keeps the identity it had, and does not consume a second place in the session. While it is away it stops showing as connected, but its place is held for it, so it is still there for the next song. The host sees it return rather than seeing a stranger appear alongside a ghost.

**Why this priority**: Without it, the capacity limit is not meaningful — a phone that flaps twice would exhaust the roster, and the capacity rejection could not be tested honestly. It is P3 because it only becomes observable after joining and refusal both work.

**Independent Test**: Connect the real peer, force it to drop and reconnect with the same device identity, then assert the session roster size is unchanged, the roster entry is the same one, the phone left and re-entered the connected list, and its connection identity is new and different from the previous one.

**Acceptance Scenarios**:

1. **Given** a phone was connected and its connection dropped, **When** it reconnects presenting the same device identity, **Then** it reuses its existing roster entry rather than creating a second one.
2. **Given** a phone reconnects with the same device identity, **When** the TV admits it, **Then** it issues a new connection identity that differs from the one the phone previously held.
3. **Given** the session roster is at capacity and one of its devices has dropped its connection, **When** that same device reconnects, **Then** it is admitted, whereas a previously-unseen device is refused with `session_full` even though fewer than ten phones are currently connected.
4. **Given** a phone's replacement connection has been admitted, **When** the superseded connection finishes closing, **Then** that cleanup does not remove the phone from the roster or invalidate its new connection identity.

---

### Edge Cases

- **The session cannot start at all.** The control port cannot be bound, or the network announcement cannot be published. The host is shown a blocking notice that gameplay is unavailable and the reason; dismissing it returns to the song-selection surface. The session phase stays `Open` and no invalid phase transition is attempted.
- **The TV has more than one network up.** A box with both wired and wireless connections could advertise an address the phone cannot reach, producing a QR code that scans cleanly and then fails to connect. Only the address of the network the TV is actually using for local traffic is published, so the advertised endpoint is the one that works.
- **The TV has no usable local network at all.** There is no address to advertise, so this is a session-start failure and takes the blocking-notice path rather than publishing an announcement nobody can act on.
- **Multicast is unavailable.** Announcement packets are silently dropped by the platform when the multicast lock is not held, producing a session that looks healthy but cannot be discovered. Acquiring the lock before announcing, and releasing it when the session ends, is a requirement rather than an optimisation.
- **A phone talks to a session that has already ended.** Its join code is no longer valid, so it is refused as if the code were wrong.
- **Two connections claim the same device identity at once.** The newer connection wins the roster entry; the older one is closed. Cleanup of the older connection must not tear down state that now belongs to the newer one.
- **A phone sends an unrecognised message after the handshake succeeded.** It is ignored with a warning; the connection survives. The same message during the handshake is fatal.
- **A connection that arrives and then says nothing.** It passes join-code validation but never introduces itself. It is closed after 5 seconds with the refusal close code and reason `invalid_message`. Because it never supplied a device identity, it holds no roster slot and is invisible to the connected count, so it cannot starve a real phone out of the session before it is closed.
- **A disconnected phone still occupies capacity.** Its roster entry and slot are held, so an eleventh previously-unseen device is refused with `session_full` even when only nine phones are actually connected. This is deliberate: it is what makes the returning phone's place real.
- **Host state versus companion-reported state.** The TV is the sole authority for the roster, connection identities, session identity, and the join code. Nothing a phone sends can change another phone's slot, its own connection identity, or the roster's contents.
- **A phone with a valid join code but no reachable asset server.** Out of scope for this slice: nothing here contacts the phone's asset server, so an unreachable one is not observable until the next slice.

## Requirements *(mandatory)*

### Functional Requirements

**Session identity and discoverability**

- **FR-001**: On launch, the system MUST create a session in the **Open** state, assign it a session identity that is a non-empty opaque string unique among the sessions this TV creates, and generate a join code of two random English words (adjective + noun) drawn from bundled word lists, displayed uppercase and hyphen-separated (e.g. `SWIFT-PANDA`).
- **FR-002**: The join code MUST be the session token: the same value is used to authorise control connections, encoded in the QR payload, and published in the network announcement.
- **FR-003**: A join code MUST be generated per session and MUST NOT be reused across sessions.
- **FR-004**: The system MUST publish a `_karaoke._tcp` network announcement for the session's duration, whose instance name is `KaraokeTV-<noun>` (the noun half of the join code, unique on the LAN), whose port is the control port, and whose attributes carry `code` (the full join code) and `v` (the protocol version).
- **FR-005**: The system MUST acquire the platform multicast lock before publishing the announcement and MUST release it when the session ends.
- **FR-006**: On platforms that require it, the system MUST obtain local-network permission before binding the control port or publishing the announcement.
- **FR-007**: The QR payload MUST encode the full control endpoint URL including the join code as the `token` query parameter, and MUST NOT encode a discovery-service identifier.
- **FR-008**: The control server MUST accept connections on every local interface, but the address published in the network announcement and encoded in the QR payload MUST be the IPv4 address of the network the TV is currently using for local traffic — a single address, not a list. If the TV has no such network with a usable address, session start MUST fail through the same blocking-notice path as a bind or announcement failure.

**Admission**

- **FR-009**: The system MUST validate the join code on every new control connection, and MUST refuse a connection whose token is missing or incorrect with reason `invalid_token`.
- **FR-010**: The system MUST refuse an introduction whose protocol version is not the supported version with reason `protocol_mismatch`.
- **FR-011**: The system MUST refuse an introduction missing any required field — device identity, device name, app version, or asset-server port — with reason `invalid_message`, naming the missing field in the human-readable message.
- **FR-012**: On a valid introduction the system MUST admit the phone, assign it a connection identity, and reply with the current session state carrying that identity.
- **FR-013**: Connection identities MUST be unique within a session, assigned from an incrementing counter starting at 1, and MUST be issued fresh on every accepted connection including reconnects.
- **FR-014**: The connection identity MUST be delivered only in the session state sent in direct reply to an introduction, and MUST be absent or null in any other session-state message.
- **FR-015**: The system MUST admit phones while the session is **Open** until the session roster holds 10 devices, and MUST refuse any further previously-unseen device with reason `session_full`.
- **FR-016**: Every refusal MUST deliver the reason to the phone before the connection closes, and MUST close with WebSocket code `1008` and a close reason equal to the refusal's reason code.
- **FR-017**: A connection that has passed join-code validation but has not delivered a valid introduction within 5 seconds MUST be refused. The refusal MUST follow FR-016 in full: an `error` reason of `invalid_message` is delivered to the phone first, then the connection closes with WebSocket code `1008` and close reason `invalid_message`. Such a connection holds no device identity, so it MUST NOT occupy a roster slot, appear in the connected list, or count toward capacity while it is pending.
- **FR-018**: During the handshake, a message of an unexpected type MUST be treated as fatal and close the connection. After the handshake has succeeded, a message of an unrecognised type MUST be ignored with a warning and MUST NOT close the connection.

**Roster and reconnect**

- **FR-019**: The system MUST maintain two distinct pieces of host-owned state: a **session roster** keyed by device identity, which retains an entry after that device's connection ends, and a **connected list** of devices with a live connection. Both MUST be observable, and the system MUST emit connection, disconnection, and reconnection events as they occur.
- **FR-020**: An introduction presenting a device identity already in the session roster MUST be admitted as a reclaim of that existing roster entry, MUST NOT increase the roster size, and MUST receive a new connection identity.
- **FR-021**: Reclaim admission MUST be decided from the device identity's presence in the session roster, not from whether a live connection for it currently exists.
- **FR-022**: When a new connection replaces an existing one for the same device identity, cleanup of the superseded connection MUST remove session or connection state only if that closing connection is still the active one for that device.
- **FR-023**: When a phone's connection drops and is not replaced, the system MUST remove it from the connected list as part of handling the close — before any subsequent admission decision is made — and MUST keep its session-roster entry and the capacity slot that entry holds.
- **FR-024**: A session-roster entry MUST be released by Kick, by the session ending, or by the end of a song — at a song's end, every roster entry that has no live connection MUST be dropped and its capacity slot freed. A device whose connection dropped mid-song MUST NOT lose its place before that boundary, so it still has one for the next song.
- **FR-025**: Only devices with a live connection MUST be reported in the connected-device list sent to phones and in the count shown on the join surface; retained-but-disconnected roster entries MUST NOT appear in either.

**Phase authority**

- **FR-026**: The system MUST implement the game-phase state machine so that every transition into or out of `Open`, and every transition into or out of `Error`, is accepted or rejected exactly as the normative transition table specifies, and MUST reject invalid transitions rather than silently applying them.
- **FR-027**: During this slice the phase MUST remain `Open`; no runtime path may enter `Preparing`, `Countdown`, `Live`, `Paused`, `Stopped`, `Results`, `DisconnectPaused`, or `Error`.
- **FR-028**: A failure to bind the control port or publish the network announcement MUST surface as a blocking notice stating that gameplay is unavailable, dismissible with a single acknowledgement that returns to the song-selection surface. It MUST NOT change the game phase and MUST NOT attempt an undefined transition.

**Host surface**

- **FR-029**: The system MUST present a song-selection surface at launch containing a header Join action, shown in its empty state because no library exists in this slice.
- **FR-030**: The Join action MUST open the join overlay as a modal over that surface, presenting the QR code as the dominant element with at least a four-module quiet zone, in high-contrast dark-on-light, centred and static, with the join code directly beneath it.
- **FR-031**: No animation or overlay element may intrude into the QR code or its quiet zone; the overlay's only permitted entrance motion is a single short fade or scale-fade of the modal shell.
- **FR-032**: The overlay MUST show how many phones are currently connected, updating as phones join and leave.
- **FR-033**: Dismissing the overlay MUST return to the song-selection surface without ending the session or disconnecting any phone.

**Boundaries and validation**

- **FR-034**: The TV MUST remain the sole authority for session identity, join code, roster membership, and connection identities; no companion-supplied value may override them.
- **FR-035**: Protocol payload construction, validation, admission rules, and phase-transition rules MUST live outside UI code; the join surface MUST read its state from a view model and MUST NOT perform network I/O.
- **FR-036**: Platform and framework types (sockets, announcement library, multicast lock, permissions, Compose) MUST stay confined to platform-facing layers and MUST NOT appear in the admission or phase-transition logic.
- **FR-037**: Every dependency required by this slice MUST be declared in the shared version catalogue; implementation MUST NOT introduce ad hoc dependency or version changes.
- **FR-038**: Completion MUST be evidenced by a fresh scoped `testBranch` pass for the changed classes, **and** by a passing loopback gate driven by the real out-of-process peer. Neither substitutes for the other.
- **FR-039**: No test that claims the control transport, the network announcement, or the connection lifecycle works may be satisfied by an in-process fake, and no gate may be satisfied by a skipped or conditionally-skipped test.

### Key Entities

- **Session**: The host-owned unit a phone joins. Holds a session identity, a join code, a lifecycle state (**Open** while phones may join; **Locked** and **Ended** are defined but unreachable in this slice), the session roster, and the connected list. Created at launch, invalidated when it ends.
- **Session roster**: The durable membership list, keyed by device identity, capped at 10 entries. An entry survives its device's disconnection and continues to hold its capacity slot, so a device that drops mid-song still has its place for the next one. Entries are released by Kick, by the session ending, or at a song's end, when every entry without a live connection is dropped. Neither Kick nor songs exist in this slice, so here entries are only ever added.
- **Connected list**: The live view — the subset of roster entries that currently have an open connection. This is what the join overlay counts and what the session-state message's connected-device list reports. A phone leaves it the instant its connection ends and rejoins it on reconnect, without its roster entry changing.
- **Join code**: Adjective-noun pair, displayed and published uppercase with a hyphen. Compared case-insensitively and with hyphens stripped, so `SWIFT-PANDA`, `swift-panda` and `swiftpanda` are the same code. Doubles as the session token.
- **Connected phone**: A device admitted to the session. Identified durably by its device identity (stable across reconnects, and the key of its roster entry) and transiently by its connection identity (fresh per connection). Carries a display name and the port of its asset server, which this slice records but does not contact. Its roster entry outlives any individual connection.
- **Connection identity**: Unsigned 16-bit counter value from 1, unique within a session, never reused across connections. Delivered only in the reply to an introduction. Later slices use it to route pitch data; this slice only assigns and reports it.
- **Introduction (`hello`)**: Phone → TV. Requires message type, protocol version (must be `1`), device identity (≥ 8 characters), device name (non-empty), app version (non-empty), and asset-server port (1024–65535). No additional fields are permitted.
- **Session state (`sessionState`)**: TV → Phone. Carries message type, protocol version, session identity, the two singer slots each with a connected flag and device name, the connected-device list (the live connections only, at most 10, each with device identity, display name, and state `assigned` or `connected_unassigned`, plus an optional slot), an in-song flag, an optional song time, and the connection identity — the last present only in the direct reply to an introduction. Retained roster entries with no live connection are absent from the list, which is why it carries no disconnected state. In this slice the in-song flag is always false, song time is always absent, and every device is `connected_unassigned` with no slot, because no song can start.
- **Refusal (`error`)**: TV → Phone. Carries message type, protocol version, a reason code from `invalid_token`, `protocol_mismatch`, `invalid_message`, `session_full` (with `session_locked` defined but unreachable here), and a non-empty human-readable message.
- **Game phase**: Host-owned playback state. Nine states with a fixed transition table. This slice keeps it at `Open` and proves the transition rules touching `Open` and `Error`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A phone on the same local network finds the TV and completes joining without the host typing anything, and appears in the TV's connected list within 5 seconds of the phone starting to look.
- **SC-002**: A phone scanning the on-screen QR code joins without any further discovery step, in a single scan, and the address it dialled is the one the TV is actually reachable on — no second attempt and no manual address entry. ⚠ **Only partially provable in this slice.** The address claim is verifiable by decoding the code with a stock camera app and dialling it with `mockphone`; the single-scan gesture needs a companion phone app, which does not exist. See Out-of-Scope Observation 14 — do not mark this criterion met on the address half alone.
- **SC-003**: Every one of the four refusal reasons — wrong code, unsupported version, incomplete introduction, session at capacity — is produced against a real separate peer process, with the correct reason delivered before the connection closes, 100% of the time across repeated runs.
- **SC-004**: A connection that presents a valid join code and then stays silent is closed within 5 seconds, having never appeared in the connected list or consumed a roster slot; repeating this does not degrade a real phone's ability to join.
- **SC-005**: Ten devices join a single session successfully and the eleventh previously-unseen device is refused, with no device losing its place while the eleventh is refused, including when one of the ten is disconnected at the time.
- **SC-006**: A phone that drops and returns keeps its place: its session-roster entry and the roster size are unchanged across the round trip, it is absent from the connected list while away and present again after, and its connection identity differs from the one it held before.
- **SC-007**: The connected count on the join overlay equals the number of phones with a live connection — never the roster size — on every observation of the surface's state, with the count following a join or a drop without any user action, refresh, or re-opening of the overlay.
- **SC-008**: When the session cannot start, the host sees a blocking notice explaining that gameplay is unavailable and returns to the song-selection surface on acknowledgement, with no crash and no wedged screen.
- **SC-009**: The slice's demo runs end to end without anyone editing anything mid-run, and Slice 0's fixture gates still pass unchanged.
- **SC-010**: The join and refusal behaviour is proved by at least one gate driven by a real separate peer process over a real socket; no production path in this slice is backed by a fake, a stub, a demo seed, or a no-op.

## Assumptions

- **The handshake deadline is a refusal, not a bare close.** FR-016 already requires every refusal to deliver its reason before the connection closes, this specification assigns the deadline the same `invalid_message` enum value the delivered payloads in F20 use, and all four fixture rejections send an `error` payload. A silent close would also be indistinguishable to the phone from the TV crashing, so the deadline emits the `error` frame and then closes, exactly like every other refusal.
- **Freshness is stated as ordering, not milliseconds.** The connected count and the connected list are derived from host-owned reactive state — `tv_app.md` models `connectedPhones` as a `StateFlow` and requires disconnect events to be emitted — so a number-of-milliseconds target would measure the UI toolkit rather than this slice's behaviour. The requirements therefore pin *when* the change happens relative to other work (removal completes as the close is handled, before the next admission decision) and that the surface follows without user action, both of which are directly assertable.
- **Session identity is opaque.** Appendix B.2.2 types it as a plain string with no pattern, and the fixtures use three different shapes (`sess-001`, `S1`, `sess-1`), so no format is normative. It is specified as a non-empty opaque string, unique per session, that phones must not parse.
- **Numbering.** This feature is `003-phone-joins`. `001` was Slice 0's foundation spec, removed from the working tree as stale in this change but preserved on `done/001-tv-host-foundation`. `002` is held by `002-solo-sing-playback`, a superseded implementation branch that is not merged to `master` but is still referenced by name in `CLAUDE.md`. Reusing either number for a different feature would be ambiguous, so this feature takes the next free one.
- **Asset fetching is excluded despite §2.3.19.** That section requires the TV to fetch `/manifest.json` immediately after a successful handshake, but `plan.md` explicitly puts song list and HTTP in Slice 2 and states they are out of scope here. The introduction's asset-server port is therefore recorded and left uncontacted, and the join overlay shows a placeholder count as `plan.md` permits.
- **The pitch data socket is not bound.** §2.3.5 requires the datagram socket to be bound at session start, but `plan.md` places clock sync and pitch ingress in Slice 8, and Slice 1's "one risky new thing" rule excludes a second transport. Binding it here would add an untested transport with no gate to prove it.
- **`session_locked` is defined but not exercised.** It is only reachable once a song can start, which is Slice 6 at the earliest. Its reason code is specified so the refusal vocabulary is complete, but no acceptance scenario claims it.
- **FR-006 requires no work at `targetSdk 36`, and naming when it will.** Android's Local Network Protections gate local traffic behind the `ACCESS_LOCAL_NETWORK` runtime permission, but the split permission model keys on target SDK: apps below 37 that hold `INTERNET` receive an *implicit* grant, and Google's guidance is explicit that such apps must **not** request it at runtime. This module targets 36 and declares `INTERNET`, so FR-006's "on platforms that require it" is vacuously satisfied and adding a permission request would be a defect, not a safeguard. The declaration already in the manifest is harmless and forward-looking. The trigger to revisit is bumping `targetSdk` to 37, at which point local network access is blocked by default and the request becomes mandatory — reaching it through `NsdManager`'s system picker would avoid the broad permission entirely.
- **Control port default.** The `tv_app.md` QR example and the peer process both use `8080`, and no section pins the value normatively, so `8080` is the default control port with the actual bound port always taken from configuration rather than assumed.
- **Singer slots are reported empty.** §2.3.11 requires the two singer slots in every session-state message, but slot assignment happens in Select Players, which is Slice 5. Both slots therefore report disconnected with an empty device name throughout this slice.
- **The screenshot gate does not apply yet.** `plan.md` introduces the screenshot gate in Slice 3 and warns that the previous baselines were recorded at twice the intended viewport. Slice 1 therefore ships the join surface without a committed baseline, and Slice 3 owns establishing one at the correct viewport.
- **Kick is excluded, and so is the song-end sweep.** §2.6.15.1 defines Kick on the Settings > Connect Phones screen, which `plan.md` schedules for Slice 17, and songs arrive in Slice 6. Both roster-release paths are specified here so capacity semantics are complete, but neither is reachable in this slice; roster capacity is exercised through joins and reconnects only.
- **Contracts are deferred to planning, not omitted.** The constitution requires every material producer/consumer boundary to be pinned as fully-qualified name plus method signature before implementation. This specification stays behaviour-level by design; that pinning is the planning step's output and is a precondition for implementation starting.

18. **No task owned the production join dispatch, the one component the whole slice routes through.** T016 declared `ControlConnectionHandler`, T018 made `KtorControlTransport` accept one, T035 implemented `SessionCoordinator.admit`, and T036 started the transport — but nothing implemented the handler that actually reads the peer's first frame, decodes it, calls `authorize`/`admit`, and sends the `sessionState` reply. 19. **`authorize`'s contracted return type could not express its own accept case, and the workaround admitted every token.** `contracts/domain-api.md` fixes `fun authorize(token: String?): AdmissionDecision`, but the only accepting case, `Admitted`, carries a `ConnectionId` — and no `ConnectionId` exists at token-check time. That is deliberate, not an oversight: `admit` mints the identifier, and only for a connection that actually introduces itself, so a peer that authorizes and then goes quiet holds nothing (FR-017). Because there was no representable accept value, `authorize` was left an unconditional `TODO()`, and the first T036 implementation bridged the gap by catching `NotImplementedError` and falling through to `admit`. That bridge made the token check unconditional: *any* token was accepted, so T037's "correct token" happy path would have passed just as well with a wrong one — a green gate proving nothing. A `ConnectionId(0)` sentinel was tried next and was rejected by the domain itself, since `ConnectionId` requires `1..65535`; the sentinel threw during class initialization and took 17 unrelated tests down with it. Resolved by adding a third case, `AdmissionDecision.Authorized`, which carries nothing and says exactly what authorization knows. Three consequences: T048 (`JoinCodeMatcher`) was pulled forward from US3, because `authorize` cannot check anything without it; the `invalid_token` refusal (nominally T050's) landed early, because "admit anyone" was strictly worse than an early refusal; and T037 gained a wrong-token loopback case, so acceptance is now proved against a real rejection instead of asserted alone. The token is also checked before the first frame is read rather than after, since it arrives on the connect URL (FR-009) and nothing about it depends on `hello`.

20. **`SessionCoordinator` is contractually required to hold a `HandshakeValidator` it can never use.** `contracts/domain-api.md` puts `validator: HandshakeValidator` in the binding constructor, but every method on the coordinator that could need it takes typed input: `admit(hello: Hello)` receives an already-parsed `Hello`, and there is no raw-string entry point anywhere on the contracted surface. Validation necessarily happens one layer out, on the wire frame, before anything can produce a `Hello` at all — so the property is dead by construction, not by omission, and stays `@Suppress("UnusedPrivateProperty")`. T050 wires the validator into `SessionControlConnectionHandler` instead, which is the only place that sees the raw frame. This is the same shape of defect as Observation 19: the contract describes a component boundary that the type signatures next to it make unreachable. Left in place rather than removed, because the constructor is binding and the cost is one unused field; `SessionComponent` now constructs a single validator and hands the same instance to both the coordinator and the handler, so at least there is no second, silently-divergent instance.


21. **FR-018's "logged as a warning" half cannot be implemented, because the app has no logging seam at all.** FR-018 requires that an unrecognised message type arriving *after* a successful handshake be "logged as a warning and ignored". The ignoring works and is now pinned by tests; the logging does not exist. There is no logging facility anywhere in `«main»` — no `android.util.Log`, no Timber, Napier or slf4j, not even a stray `println` — and the class that would do the logging, `SessionControlConnectionHandler`, lives in `domain.control`, which contracts/domain-api.md requires to stay pure Kotlin with no Android types. So the requirement cannot be met either by using what exists (nothing does) or by reaching for the platform (the layering forbids it). Meeting it properly needs a `Logger` port in contracts/ports.md with an adapter in `data/`, which is a planning decision and a new contract, not something to invent inside a US2 task. The observable behaviour FR-018 actually specifies — connection stays open, frame ignored, never fatal — is implemented and tested; only the diagnostic side is missing.

22. **`SessionEvent.Reconnected.previous` cannot be non-null, because the commonest reconnect supersedes nothing.** contracts/domain-api.md declares `Reconnected(deviceId, connectionId, previous: ConnectionId)` with a non-null `previous`, while declaring `RosterAdmission.Reclaimed(entry, previous: ConnectionId?)` with a nullable one. Both cannot hold. FR-021 requires reclaim to be decided from roster presence alone, *not* from whether a live connection exists, and FR-023 requires a dropped device to keep its entry with `connection = null`. So the ordinary reconnect — phone drops, phone comes back, which is exactly what SC-006 and the T055 gate case exercise — reaches `Reclaimed` with `previous == null`. There is no sentinel escape: `ConnectionId` requires `1..65535`, so a placeholder is not constructible, and a companion-object constant holding one throws during class initialization (this already cost this slice 17 test failures once, see Observation 19). Nor can the entry keep its last `ConnectionId` after `detach` without inventing roster state that data-model.md does not describe. **Resolution: `Reconnected.previous` becomes `ConnectionId?`.** `null` then means "this device had no live connection to supersede", which is information the UI genuinely wants, and non-null means a live connection was displaced (FR-022). The alternative — emitting `Connected` when `previous` is null — was rejected because it discards the fact that a *returning* device rejoined, which is precisely what FR-019 requires to be observable.

25. **The declared Phase E coverage gate could not pass, because its only two branches are compiler-generated and one of them is unreachable.** plan.md named the Phase E `testBranch` selection as `JoinViewModel` plus `QrPayloadEncoder`. Neither class contains a single branch of its own: `QrPayloadEncoder` is one string expression, and `JoinViewModel`'s logic is all delegation. The entire bundle's BRANCH counter therefore came from the synthetic `JoinViewModel$uiState$1` class the Kotlin compiler emits for the `combine {}` suspend lambda, whose `invokeSuspend` compiles to a `tableswitch` with a `default` arm that throws `IllegalStateException("call to 'resume' before 'invoke'")`. That arm is dead defensive code no test can reach, so the gate read BRANCH 1/2 = 0.50 against a 0.70 minimum and would have failed forever. Fixed in T061 by adding `QrBitmapRenderer` — already named in Phase E's own scope sentence, and contributing 6/6 real covered branches — which brings the bundle to BRANCH 7/8 and LINE 34/37 while still counting the unreachable branch rather than suppressing it. **Related and now verified: `com.couchraoke.quality.NoCoverageGenerated`, the annotation the `implementation` skill instructs agents to apply to compiler-generated code, does not exist anywhere in this repository.** `quality-conventions/` defines no such annotation and the JaCoCo configuration has no exclude mechanism beyond `jdk.internal.*`, so there is currently no supported way to exempt synthetic code from a coverage gate. Either the annotation should be implemented in `quality-conventions/` or the skill should stop naming it; the workaround in the meantime is to ensure any `--src` selection contains enough genuinely branching production code that a single compiler artifact cannot decide the outcome. `quality-conventions/` is consent-gated, so this is reported, not fixed.

26. **A misspelled or wrongly-packaged `--src`/`--test` FQCN is silently ignored by `testBranch`, so a gate can report a confident pass while measuring less than it claims.** Found while running T064. `JoinCodeMatcher` and `HandshakeValidator` live in `com.couchraoke.tv.domain.control`, but an ad-hoc phase gate run during T064 named `com.couchraoke.tv.domain.session.JoinCodeMatcher` and `…session.JoinCodeMatcherTest`. The build printed `BUILD SUCCESSFUL`, produced a coverage report, and satisfied both thresholds — having quietly dropped the class from the selection entirely. Nothing in the output distinguishes "this class passed" from "this class was never measured". The authoritative feature-level gate in plan.md, whose FQCNs were checked against the tree first, does measure it: `JoinCodeMatcher` contributes BRANCH 10/10, which the mistyped run omitted. The practical consequence is that a `--src` list is not self-validating and a green scoped gate is only as trustworthy as the spelling of its arguments. Suggested fix, out of scope here because `quality-conventions/` is consent-gated: have the `testBranch` task resolve every `--src` and `--test` argument against the compiled classes and fail fast on any that matches nothing. Until then, verify the per-class breakdown in `testBranchJacocoReport.xml` lists every class the gate names, rather than trusting the bundle total.
27. **Most of T065's discovery half is provable without an Android device, and now is; what remains device-only is the multicast lock.** T065 bundles two claims that separate cleanly. The first — that the TV registers the mDNS service, publishes the right TXT record, and a real peer can find and join it knowing only the service type — needs a real multicast socket but not Android, because discovery here is **not** OS functionality: research.md R4 rejected `NsdManager` in favour of jmDNS 3.6.2, a userspace library running in our own process, and there are zero `NsdManager` references in the tree. `LanDiscoveryProbe` now proves that first claim by running the real `SessionComponent.startSession` path over a developer machine's LAN interface and having the real peer join by mDNS alone, with no `--tv-host` and no `--token` on the command line so the address, port and join code can only have come from the announcement. Verified non-vacuous by tripwire (no-op announcer → exit 5) and confirmed opt-in-skipped by default, since it needs a network that permits multicast and would otherwise report a network policy as a product defect. The second claim is `WifiManager.MulticastLock`. Android's WiFi driver discards multicast before it reaches userspace to save power, and that lock is the opt-out; a desktop JVM has no such filtering, so the probe substitutes a no-op lease and `WifiMulticastLease` remains executed by nothing, anywhere. Its failure mode is silent — jmDNS registers without error and is simply never found — so no unit, screenshot, coverage or loopback gate can distinguish a held lock from an absent one. That is the irreducible reason T065 needs hardware, and it is now the only reason.
